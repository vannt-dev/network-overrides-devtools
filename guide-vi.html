1. Giới thiệu

Network Overrides DevTools là extension Chrome/Edge cho developer, dùng để chặn và ghi đè response của API ngay trong trình duyệt, không cần sửa code backend.

Công dụng chính

  • Mock API response để test frontend khi backend chưa sẵn sàng.
  • Debug bằng cách đổi response để thử các trạng thái khác nhau (lỗi, dữ liệu rỗng, trường hợp biên).
  • Chuyển request từ API cũ sang API mới mà không sửa code frontend.
  • Xem nhanh các API request đã bắt và chép thành lệnh cURL.

2. Cài đặt

Yêu cầu

  • Chrome hoặc Microsoft Edge (bản mới nhất).
  • Extension được nạp dạng unpacked từ source.

Các bước

  1. Mở chrome://extensions (hoặc edge://extensions).
  2. Bật Developer mode (góc trên bên phải).
  3. Bấm Load unpacked.
  4. Chọn thư mục gốc của project (thư mục chứa manifest.json).
  5. Icon extension sẽ xuất hiện trên thanh toolbar.

Kiểm tra

  • Icon extension xuất hiện trên thanh toolbar.
  • Mở DevTools (F12) → tab Overrides.

3. Giao diện

3.1. Popup

Bấm icon extension trên toolbar. Popup gồm:

  • Tiêu đề: "Network Overrides API" với hai nút nhỏ: Làm mới danh sách request và Mở hướng dẫn sử dụng.
  • Bật ghi đè: bật/tắt tính năng ghi đè.
  • Ngôn ngữ: Tự động, English hoặc Tiếng Việt (xem 9.14).
  • 3 tab:
    • API đã bắt (N): các request đã bắt, đếm theo thời gian thực, nhóm theo loại resource (XHR, Fetch, Doc, JS, CSS).
    • Đã ghi đè (N): số API đang khớp một rule đang bật, đếm theo thời gian thực.
    • Rule (N): tổng số và danh sách mọi rule đã lưu.
  • Ô tìm kiếm: lọc API theo một phần của URL.

3.2. DevTools Panel

Mở DevTools (F12) → tab Overrides. Giống popup, có thêm:

  • Form nhập nhanh: form thêm rule nhanh (pattern + body) phía trên tab Rule.
  • Tự nạp HAR: khi mở panel, tự nạp lịch sử request từ chrome.devtools.network.getHAR().

3.3. Modal tạo/sửa rule

Bấm Mock request này trên một API (hoặc bấm vào dòng API) để mở modal. Modal hiện các field hay dùng trước:

  • Mẫu nhanh: một click điền sẵn các field bên dưới. Danh sách rỗng (status 200 và [], hoặc chính object JSON đó với các mảng bị làm rỗng), Lỗi server (status 500), Chậm (3 s) (delay 3000 ms), Mất mạng (lỗi mạng, InternetDisconnected), và Bỏ CSP, Không cache: giữ response thật và bỏ các header Content-Security-Policy hoặc header cache của nó (xem 6.10).
  • URL pattern: pattern để khớp URL. Ban đầu là URL của request và sửa được: dùng * để khớp nhiều URL hơn, vd. /api/users/*.
  • Method: danh sách (Bất kỳ, GET, POST, PUT, PATCH, DELETE) để giới hạn rule theo method. Mặc định là Bất kỳ, khớp mọi method. Khi mở từ một API đã bắt, method được điền sẵn theo request đó.
  • Mock response / Chuyển hướng / Lỗi mạng / WebSocket: chọn loại rule.
  • Status code (mock response): để trống thì giữ status thật. Được điền sẵn từ request đã bắt nếu status đó mang được body.
  • Response body: nội dung response tự đặt (với mock response).
  • URL chuyển hướng: URL đích, dùng được * để thay giá trị.
  • Định dạng JSON: làm đẹp JSON body.
  • Lưu rule: lưu rule.

Các tùy chọn còn lại nằm trong mục Nâng cao (thu gọn sẵn), chia nhóm:

  • Điều kiện: GraphQL operation (xem 5.8), query parameter, request header và đoạn text mà request body phải chứa (xem 5.7), và Áp dụng trên mọi trang (rule toàn cục).
  • Thời gian & lỗi: Độ trễ (ms); Giả lập lỗi mạng cho loại Lỗi mạng (Failed, TimedOut, ConnectionRefused, NameNotResolved, InternetDisconnected; kết hợp TimedOut với delay dài để giả lập timeout thật); và Trả lời mà không gọi server (mock response: request được trả lời ngay trong trình duyệt trước khi gửi đi, nên server không bao giờ bị gọi và host không truy cập được vẫn nhận mock; status để trống = 200; CORS preflight được trả lời giúp bạn).
  • Response header: header thêm vào response (mỗi dòng một Header-Name: value; trùng tên thì ghi đè header gốc), và Header cần bỏ khỏi response (xem 6.10).
  • Kiểu body: patch & script: response body là Text, Base64 thô, Script (JavaScript), Patch JSON response thật (xem 6.6) hoặc Giữ response thật (chỉ sửa header) (xem 6.10), và có điền placeholder {{...}} hay không.
  • Response ngẫu nhiên: thêm các response khác cho rule, mỗi cái có trọng số, và seed để thứ tự lặp lại được (xem 6.11).
  • Đổi request: thay request body gửi tới server, thêm hoặc thay request header.

Nhóm nào đang có giá trị sẽ hiện số đếm trên tiêu đề và tự mở ra khi bạn sửa rule, nên không thiết lập nào bị giấu.

4. Cách dùng cơ bản

Bước 1: Mở extension

  • Cách A: bấm icon extension trên toolbar → mở popup.
  • Cách B: mở DevTools (F12) → tab Overrides.

Bước 2: Bật ghi đè

Gạt Bật ghi đè sang ON.

Extension sẽ gắn debugger vào tab hiện tại và bắt đầu theo dõi request.

Bước 3: Bắt API

Dùng ứng dụng như bình thường. Các API request sẽ tự xuất hiện trong tab API đã bắt.

Bước 4: Tạo rule

Cách 1 (bấm vào API):

  1. Vào tab API đã bắt hoặc Đã ghi đè.
  2. Bấm Mock request này trên API muốn ghi đè (bấm vào dòng cũng vậy). Nếu đã có rule áp dụng cho API này, modal mở rule đó để sửa.
  3. Modal mở với pattern và status thật được điền sẵn, và Method chọn sẵn theo method của request nếu đó là GET/POST/PUT/PATCH/DELETE (nếu không thì là Bất kỳ).
  4. Nếu API có response body đã lưu, body được tự điền.
  5. Sửa nội dung → Lưu rule.

Cách 2 (nhập tay, chỉ ở DevTools panel):

  1. Vào tab Rule.
  2. Trong form phía trên, nhập Pattern và Response body.
  3. Bấm Thêm thủ công.

Bước 5: Kiểm tra

  • API bị ghi đè có viền xanh trong danh sách.
  • Tab Đã ghi đè hiện số lượng và danh sách API đang khớp.
  • Response thật được thay bằng nội dung của bạn.

Bước 6: Tắt

  • Gạt công tắc sang OFF để tắt mọi rule.
  • Hoặc vào tab Rule → bấm Xóa trên rule cần bỏ.

5. URL pattern

5.1. Chuỗi con (mặc định)

Mọi URL chứa chuỗi pattern đều khớp.

Pattern:  /api/users
Matches:  https://example.com/api/users
          https://example.com/api/users/123
          https://example.com/v2/api/users/list
No match: https://example.com/api/admin

5.2. Wildcard *

Dùng * để khớp một đoạn bất kỳ của URL. Mỗi * cũng bắt giá trị đã khớp để dùng trong URL chuyển hướng. 

Pattern:  /api/*/users/*
Matches:  /api/v1/users/123  → captures: ["v1", "123"]
          /api/v2/users/abc  → captures: ["v2", "abc"]

5.3. Regex /pattern/flags

Pattern bắt đầu và kết thúc bằng / được hiểu là regex. Flag (nếu có) đặt sau dấu / cuối. 

Pattern:  /\/api\/v\d+\/users/i
Matches:  /api/v1/users (case-insensitive)
          /API/V2/Users
No match: /api/admin/users
Pattern:  /\/api\/user\/(\d+)/
Matches:  /api/user/42 (captures: ["42"])

5.4. Khớp tất cả

Pattern: *
Pattern: all

Khớp mọi request.

5.5. Thứ tự rule

Rule được xét theo thứ tự trong danh sách. Rule đầu tiên khớp sẽ được dùng. Để đổi ưu tiên, kéo rule bằng tay cầm ⠿ và thả vào nửa trên hoặc nửa dưới của rule khác, hoặc focus tay cầm rồi bấm phím mũi tên lên/xuống. Thứ tự mới được lưu ngay. Rule của domain luôn chạy trước rule toàn cục, nên rule chỉ di chuyển trong nhóm của nó.

5.6. HTTP method

Ngoài URL pattern, rule còn có thể giới hạn theo HTTP method qua field Method trong modal (xem 3.3 và 4). Rule có method cụ thể (GET, POST, PUT, PATCH, DELETE) chỉ áp dụng cho request dùng method đó; Bất kỳ (mặc định) khớp mọi method, với mọi kiểu pattern.

5.7. Điều kiện query, header và body

Mở Nâng cao → Điều kiện trong modal để thu hẹp rule về một số request cùng URL. Mọi điều kiện bạn điền đều phải đúng, cùng với pattern và method. Để trống thì rule khớp như cũ.

  • Query parameter: viết như trong URL, ví dụ page=2&debug. page=2 cần page bằng 2 (một trong các giá trị, nếu lặp lại; so sánh sau khi URL decode). debug đứng một mình cần debug có mặt, giá trị bất kỳ. Tên phân biệt hoa thường.
  • Request header: mỗi dòng một header. X-Tenant: acme cần header đó với đúng giá trị đó; Authorization đứng một mình chỉ cần header có mặt. Tên header không phân biệt hoa thường.
  • Request body chứa: request body phải chứa đoạn text này, ví dụ "plan":"pro". Phân biệt hoa thường. Nếu trình duyệt không đưa body cho extension (ví dụ upload dạng stream), điều kiện không khớp.

Dòng của rule trong danh sách rule có hiện điều kiện, ví dụ + query page=2. CORS preflight không mang header lẫn body của request phía sau, nên với preflight chỉ điều kiện query được xét.

5.8. GraphQL operation

Field GraphQL operation thu hẹp rule về một operation gửi tới URL chung như /graphql. Rule khớp khi operationName trong JSON request body bằng giá trị này (không phân biệt hoa thường); nếu không có thì khi query chứa giá trị; nếu không nữa thì khi body thô chứa giá trị. Request không có body thì không khớp.

6. Body ghi đè

6.1. Chế độ Text

Nội dung được mã hóa base64 và trả về làm response body.

{
  "status": "ok",
  "data": [
    { "id": 1, "name": "Alice" },
    { "id": 2, "name": "Bob" }
  ]
}

6.2. Chế độ Base64 thô

Dùng khi bạn đã có nội dung mã hóa base64 (ví dụ dữ liệu nhị phân, ảnh, file đã mã hóa sẵn).

6.3. Nhãn kiểu body

  • text — nội dung không phải JSON hợp lệ.
  • json — nội dung là JSON hợp lệ (tự nhận ra khi bạn gõ).

6.4. Định dạng JSON

Bấm Định dạng JSON để làm đẹp response body. Nếu nội dung không phải JSON hợp lệ, nút báo lỗi và không đổi gì.

6.5. Tự điền

Khi tạo rule mới từ một API:

  • Nếu API có response body đã lưu (trong recentApiBodies), body được điền sẵn.
  • Nếu không, extension gửi message getApiData tới background worker để lấy body đã lưu.
  • Tính năng này chỉ chạy khi Auto-fill on open đang bật (mặc định: bật).

6.6. Patch JSON response thật

Chọn Patch JSON response thật trong danh sách Response body là khi bạn muốn giữ dữ liệu thật và chỉ đổi vài trường, ví dụ bật gói trả phí hoặc ẩn banner. Request vẫn tới server; rule chỉ đổi các trường bạn liệt kê trong JSON response. Mỗi dòng một thay đổi: 

set data.user.plan = "pro"
remove data.ads
set data.items[0].price = 0
set data.flags = {"beta": true}
  • set <path> = <value> đặt giá trị tại path. Giá trị là JSON: text viết trong ngoặc kép ("pro"), còn số, true, false, null, object và mảng viết như bình thường.
  • remove <path> xóa một trường, hoặc một phần tử mảng (các phần tử sau dồn lên).
  • Path dùng dấu chấm cho trường và [0] cho phần tử mảng: data.items[0].name. Key có dấu chấm, dấu cách hoặc = thì đặt trong ngoặc kép: data["user.name"]. Path bắt đầu bằng / là JSON Pointer: /data/items/0/name.
  • [-] (hoặc - trong JSON Pointer) là cuối mảng: set data.items[-] = {"id": 99} thêm một phần tử.
  • Khi path của set chưa tồn tại, các object còn thiếu được tạo ra (là mảng khi phần kế tiếp là [0] hoặc [-]). remove một thứ không có thì không làm gì.

Status và header thật được giữ; Status code, Response header và Độ trễ vẫn áp dụng nếu bạn điền. Content-Length được tính lại cho body mới. JSON được trả về dạng gọn. Placeholder không được điền trong giá trị patch, và không có tùy chọn Trả lời mà không gọi server, vì patch cần response thật.

Khi response không phải JSON hoặc không có body (trang HTML, 204, redirect), nó đi qua nguyên vẹn và panel hiện cảnh báo. Thay đổi nào không áp dụng được, như path đi qua một trường text hoặc chỉ số mảng vượt quá cuối, sẽ bị bỏ qua và được nêu trong cùng cảnh báo; các thay đổi khác vẫn áp dụng. Dòng của rule trong tab Rule kết thúc bằng patch N fields; rê chuột lên để xem các thay đổi.

6.7. Response bằng script

Với kiểu body Script (JavaScript), rule tự tính response. Body là thân của một hàm async nhận request và trả về response: 

// Keep the real response, but only its first three items.
const data = JSON.parse(request.response.body);
return { status: 200, body: { ...data, items: data.items.slice(0, 3) } };
  • request có url, method, headers (tên viết thường), query, params (phần mà mỗi * khớp), body, response (status, headers và body gốc) và vars (các biến của bạn, xem 9.15).
  • Trả về một string làm body, { status, headers, body }, hoặc giá trị khác để gửi dạng JSON. Status hay header trả về sẽ thắng cấu hình của rule; delay vẫn áp dụng. Placeholder không được điền trong script.
  • Script chạy trong trang đang inspect, nên dùng được fetch, localStorage và biến toàn cục của trang. Script có 5 giây; script ném lỗi, không trả gì hoặc quá giờ sẽ trả status 500 kèm header x-network-overrides-error: script.
  • Rule nhập vào có thể chứa script, và script chạy trong các trang mà rule khớp: chỉ nhập file bạn tin cậy.

6.8. Thay một file tĩnh

Rule Mock response cũng trả lời được script, stylesheet, ảnh, font và trang. Đặt URL pattern trỏ tới file, ví dụ /static/app.js, rồi bấm Dùng file trên máy… dưới ô body:

  • File chữ (JS, CSS, HTML, JSON, SVG, XML) được đưa vào ô body, vẫn sửa được. File khác (ảnh, font) được giữ nguyên và hiện là Từ file tên (dung lượng), kèm nút Bỏ file.
  • Content-Type được đặt theo file và đổi được ở Nâng cao → Response header. Rule trả về status 200 nếu bạn không đặt status khác, nên file mà server không có (404) vẫn tải được.
  • Rule được lưu trong bộ nhớ của trình duyệt, tổng cộng khoảng 10 MB. Trên 2 MB editor sẽ cảnh báo; hãy giữ file nhỏ, hoặc chỉ thay file bạn đang làm.
  • Khi một tab đang được chặn request, cache của trình duyệt bị bỏ qua, nên rule vẫn áp dụng cho file trang đã cache. Tải lại trang sau khi thêm rule.
  • Script hay stylesheet có thuộc tính integrity (SRI) sẽ từ chối file đã thay. Request do service worker tự trả lời thì không bị chặn.

6.9. Chèn JS/CSS vào trang

Chọn kiểu Chèn JS/CSS để thêm code của bạn vào các trang khớp rule, ví dụ https://example.com/*. Trang thật vẫn tải; rule chỉ thêm vào.

  • Stylesheet được đặt ở cuối <head>; script ở cuối <body>, nên khi chạy thì các phần tử của trang đã có.
  • Chỉ trang (document) bị thay đổi, không phải API, và chỉ response HTML UTF-8 thành công (2xx). Rule khác, như mock API, vẫn chạy trên cùng trang.
  • Trang có Content-Security-Policy vẫn giữ nó. Hash SHA-256 của script và stylesheet được chèn được thêm vào policy, nên đúng code đó được chạy, còn code inline của chính trang và mọi quy tắc khác của policy vẫn như cũ. CSP sandbox không có allow-scripts vẫn chặn script; khi đó panel sẽ cảnh báo.
  • Nếu code của bạn tải thêm script khác, dùng eval hoặc event handler inline, policy vẫn có thể chặn phần đó. Khi đó mới tick Bỏ Content-Security-Policy của trang trong rule: các trang khớp sẽ tải mà không có CSP khi rule đang bật, nên kém an toàn hơn.
  • Tải lại trang sau khi thêm hoặc sửa rule.

6.10. Giữ response thật, bỏ header

Rule có thể bỏ header khỏi response, ví dụ Content-Security-Policy đang cản việc debug, hoặc các header cache làm trình duyệt giữ file cũ.

  • Chọn Giữ response thật (chỉ sửa header) trong Nâng cao → Kiểu body để giữ nguyên body của server. Request vẫn đến server; chỉ status (nếu bạn đặt) và header thay đổi. Mẫu nhanh Bỏ CSP và Không cache thiết lập việc này bằng một click.
  • Liệt kê header trong Nâng cao → Response header → Header cần bỏ khỏi response, mỗi dòng một tên hoặc cách nhau bằng dấu phẩy. Không phân biệt hoa thường. Tên kết thúc bằng * bỏ mọi header bắt đầu bằng phần trước nó: x-debug-*.
  • Việc bỏ header cũng dùng được với mọi mock response: header của server bị bỏ trước, rồi response header của rule mới được thêm vào. Vì vậy bạn có thể bỏ Cache-Control rồi thêm Cache-Control: no-store.
  • Header đánh dấu của extension không bao giờ bị bỏ.
  • Response không đọc được body, như redirect, được cho đi qua không đổi và panel sẽ cảnh báo. Không có tùy chọn Trả lời mà không gọi server, vì rule cần response thật.

6.11. Response ngẫu nhiên theo trọng số

Rule Mock response (body Text hoặc Base64 thô) có thể trả về một trong nhiều response, để xem trang xử lý thế nào khi API chập chờn. Viết body và status như thường: đây là response thứ nhất. Rồi mở Nâng cao → Response ngẫu nhiên, bấm + Thêm response và điền trọng số, status (để trống thì dùng status của rule), body và header (Name: value, thêm đè lên header của rule). Trọng số của response ở trên là trọng số của response thứ nhất (để trống là 1).

  • Mỗi request nhận một response, chọn theo trọng số: trọng số 80 và 20 cho response đầu khoảng 8 lần trên 10. Trọng số 0 không bao giờ được chọn. Placeholder và biến dùng được trong mọi body.
  • Response kèm header x-network-overrides-response: số thứ tự của response đã trả (1 là response của chính rule).
  • Seed (thứ tự lặp lại được): để trống thì chọn ngẫu nhiên. Có một số thì các lần chọn theo cùng một thứ tự mỗi lần, hợp cho test tự động. Thứ tự đi theo số lần rule đã được áp dụng, nên vẫn tiếp tục khi worker khởi động lại; Đặt lại số đếm, hoặc sửa rule, sẽ bắt đầu lại từ đầu.

7. Chuyển hướng URL

7.1. Cách hoạt động

Khi chọn loại Chuyển hướng, thay vì ghi đè response body, extension chuyển request sang URL khác ngay ở giai đoạn request (trước khi request thật được gửi).

7.2. Thay wildcard

Dùng * trong URL chuyển hướng để thay bằng các giá trị đã bắt khi khớp pattern.

Pattern Request URL Giá trị bắt URL chuyển hướng Kết quả
/api/* https://site.com/api/user ["user"] https://site.com/api/v2/* https://site.com/api/v2/user
/api/old/*/data /api/old/v1/data ["v1"] /api/new/*/data /api/new/v1/data
https://old.com/*/item/* https://old.com/shop/item/5 ["shop","5"] https://new.com/*/product/* https://new.com/shop/product/5

Nếu còn * nào chưa được thay, extension ghi lỗi vào log và để request đi bình thường (không chuyển hướng).

Lỗi hay gặp: pattern có 1 * nhưng URL chuyển hướng có 2:

Pattern Request URL Giá trị bắt URL chuyển hướng Kết quả
https://site.com/api/* https://site.com/api/user ["user"] https://site.com/api/v2/** ❌ * thứ hai không được thay

7.3. Khi nào nên dùng

  • Chuyển từ API cũ sang API mới mà không sửa code frontend.
  • Trỏ request từ production sang server staging/local để debug.
  • Chặn một số request bằng cách chuyển chúng tới một endpoint rỗng.

8. Quản lý rule

8.1. Xem rule

Vào tab Rule. Mỗi rule hiện:

  • Ô bật/tắt: ở đầu dòng. Bỏ chọn nghĩa là rule đang tắt (xem 8.5).
  • Nhãn TOÀN CỤC: rule áp dụng trên mọi trang.
  • Tóm tắt một dòng: rule khớp gì → rule làm gì, ví dụ GET /api/orders + query page=2 → 500 · chậm 3 s, POST /graphql (op: GetUser) → patch 2 fields, /api/* → lỗi mạng hoặc ws wss://example.com/socket → thay frame. Rê chuột lên để xem chi tiết; bấm vào để mở trình sửa.
  • Số lần áp dụng: con số nhỏ sau rule, số lần rule được áp dụng trong phiên này. 0 màu xám, số lớn hơn màu xanh. Rê chuột lên (hoặc Tab tới) để xem lần áp dụng gần nhất và URL nào. Một request chỉ được đếm khi rule thật sự đổi nó. Rule đang bật mà vẫn 0 sau khi đã có request đi qua sẽ có viền đứt: kiểm tra pattern, method và điều kiện. Số đếm đi theo rule khi bạn đổi thứ tự hoặc tắt rồi bật lại, và đếm lại từ đầu khi bạn sửa rule. Đặt lại số đếm phía trên danh sách đưa mọi số về 0, tắt chặn request cũng vậy. Số đếm không bao giờ được lưu, xuất hay nhập cùng rule.

8.2. Sửa rule

Bấm Sửa cạnh rule (hoặc bấm vào phần tóm tắt) → modal mở với giá trị hiện tại → sửa → Lưu rule. Nhân bản tạo bản sao của rule.

8.3. Xóa rule

Bấm Xóa → rule bị xóa ngay.

8.4. Lưu trữ

Rule được lưu trong chrome.storage.local → không bao giờ mất khi tải lại trang, đóng DevTools hay khởi động lại trình duyệt.

8.5. Bật/tắt một rule

Mỗi rule có một ô chọn ở đầu dòng. Bỏ chọn sẽ tắt rule (enabled: false) mà không xóa:

  • Rule vẫn hiện trong danh sách Rule, nhưng mờ đi.
  • API mà rule nhắm tới vẫn nằm trong tab Đã ghi đè (vẫn "sẽ khớp" theo pattern và method) nhưng cũng hiện mờ, vì rule đã tắt không còn được áp dụng.
  • Background service worker bỏ qua rule đã tắt khi chọn rule để áp dụng cho request.

Chọn lại ô sẽ bật lại rule. Rule mới, và rule có từ trước khi có tính năng này, mặc định là bật.

8.6. Xuất rule

Bấm Xuất trong tab Rule để tải các rule của domain hiện tại về thành file JSON (đặt tên theo domain). File có dạng: 

{
  "version": 1,
  "domain": "https://example.com",
  "exportedAt": "2026-07-07T00:00:00.000Z",
  "overrides": [
    /* OverrideRule[] */
  ]
}

Chỉ xuất rule của domain đang mở trong panel, không phải mọi domain.

8.7. Nhập rule

Bấm Nhập → File rule (.json) trong tab Rule và chọn một file JSON đã xuất trước đó (hoặc tự viết):

  • Nếu file có field domain và không khớp domain đang mở trong panel, một hộp thoại cảnh báo và hỏi có nhập vào domain hiện tại không. Hủy thì không có gì thay đổi.
  • Nếu domain hiện tại đã có rule, một hộp thoại hỏi cách gộp: Thêm vào cuối thêm các rule nhập vào cuối danh sách hiện có; Thay toàn bộ thay mọi rule của domain hiện tại bằng các rule nhập vào. Đóng hộp thoại là hủy việc nhập.
  • Nếu domain hiện tại chưa có rule, rule được nhập luôn, không hỏi.
  • File không hợp lệ (không phải JSON hợp lệ, thiếu mảng overrides, hoặc có rule thiếu field bắt buộc) bị từ chối kèm thông báo, và không có gì thay đổi.
  • Chỉ các field rule đã biết (pattern, mode, body, redirectUrl, method, enabled) được giữ lại từ mỗi rule nhập vào; các thuộc tính khác trong file bị bỏ.
  • Các điều kiện khớp matchQuery, matchHeaders và matchBody (xem 5.7) cũng được giữ. File xuất từ trước khi có chúng vẫn nhập được như cũ.
  • Rule patch ("mode": "patch", xem 6.6) giữ danh sách patch gồm các thao tác { "op": "set" | "remove", "path": "...", "value": ... }. File có thao tác patch sai định dạng bị từ chối như mọi file không hợp lệ khác.
  • removeResponseHeaders, "mode": "passthrough" và response ngẫu nhiên (responses, weight, randomSeed) cũng được giữ. Biến không nằm trong file.

Giống Xuất, Nhập luôn làm việc trên domain đang mở trong panel, không bao giờ trên mọi domain cùng lúc.

9. Tính năng khác

9.1. Chép cURL

Mỗi API có nút cURL. Bấm để chép request thành lệnh cURL:

curl 'https://api.example.com/data' \
  -X 'POST' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer xxx' \
  --data-raw '{"key":"value"}'

9.2. Tìm API

Ô tìm kiếm ở tab API đã bắt và Đã ghi đè. Tìm theo một phần của URL (không phân biệt hoa thường). Phần khớp được tô nền vàng.

9.3. Làm mới danh sách API

Bấm Làm mới danh sách request trên tiêu đề hoặc nút làm mới cạnh bộ lọc. Icon quay và tạm khóa trong lúc nạp danh sách API. Nếu danh sách rỗng, extension tự thử lại.

9.4. Mở hướng dẫn sử dụng

Bấm Mở hướng dẫn sử dụng trên tiêu đề. Hướng dẫn mở trong một tab riêng, nên popup hay DevTools panel vẫn dùng được. Hướng dẫn mở theo ngôn ngữ extension đang hiện: bản tiếng Việt này khi giao diện là Tiếng Việt, bản tiếng Anh trong các trường hợp khác.

9.5. Nhóm theo loại

API được nhóm theo loại resource: XHR, Fetch, JS, CSS, Img, Media, Font, Doc, WS, Manifest, EventSource, TextTrack, Other.

Bấm tiêu đề nhóm để thu gọn/mở rộng. Trạng thái thu gọn được lưu lại.

9.6. Header đánh dấu

Khi một request bị ghi đè, extension thêm các response header sau:

  • x-network-overrides: true
  • x-network-overrides-pattern: <pattern>
  • x-network-overrides-response: <n>, chỉ với rule có response ngẫu nhiên: response nào đã được trả

Nhờ đó bạn dễ nhận ra request bị ghi đè trong tab Network của DevTools.

9.7. Response động bằng placeholder

Chèn placeholder động vào body của mock response:

  • {{$uuid}} — UUID v4 ngẫu nhiên
  • {{$isoDate}} — thời điểm dạng ISO 8601
  • {{$epoch}} — Unix timestamp tính bằng ms
  • {{$randomEmail}} — địa chỉ email ngẫu nhiên
  • {{$randomName}} — họ tên ngẫu nhiên
  • {{$randomInt(1, 100)}} — số nguyên ngẫu nhiên trong khoảng
  • {{$query(name)}} — giá trị query parameter trong URL của request
  • {{$jwt}} — JWT giả nhưng đúng định dạng, có sub, iat (lúc này) và exp (lúc này + 1 giờ). Thêm claim bằng object JSON và đặt thời gian sống tính bằng giây: {{$jwt({"sub":"42","role":"admin"}, 300)}}. Thời gian âm cho token đã hết hạn; trong chuỗi JSON có thể viết dấu nháy là \". Token không có chữ ký hợp lệ: chữ ký là ngẫu nhiên, nên chỉ hợp với code chỉ giải mã token, không qua được bước kiểm tra chữ ký.

9.8. Rule toàn cục (mọi domain)

Chọn Nâng cao → Điều kiện → Áp dụng trên mọi trang (rule toàn cục) để chặn các request khớp trên mọi domain. Rule toàn cục có nhãn TOÀN CỤC trong danh sách rule.

9.9. Đổi payload của request

Ghi đè payload của request POST, PUT hoặc PATCH trước khi tới server, trong Nâng cao → Đổi request.

9.10. Giới hạn mạng và thống kê traffic

Dùng danh sách Mạng để giả lập Fast 3G, Slow 3G hoặc Mất mạng cho tab đang gắn. Bộ đếm trực tiếp hiện số request đã ghi đè và bị lỗi, và vẫn giữ khi service worker khởi động lại.

9.11. Nhập file HAR

Trong tab Rule, bấm Nhập → cURL hoặc OpenAPI / Swagger… rồi dán hoặc chọn một file .har (HTTP Archive) để tạo hàng loạt mock rule từ traffic đã ghi. Cùng hộp thoại đó nhận cả lệnh cURL hoặc spec OpenAPI / Swagger.

9.12. Phím tắt trong trình sửa

  • Ctrl + Enter / Cmd + Enter — lưu rule
  • Ctrl + Shift + F / Cmd + Shift + F — định dạng JSON body

9.13. WebSocket frame

Để đổi nội dung một WebSocket, mở modal (hoặc bấm một mục WS trong danh sách API) và chọn WebSocket. Rule khớp URL của socket (wss://api.example.com/*), chiều (gửi, nhận hoặc cả hai) và, nếu cần, text của frame (chứa, hoặc regex). Rule đang bật đầu tiên phù hợp sẽ được áp dụng:

  • Thay cả frame: frame được thay bằng body (dùng được placeholder như {{now}}).
  • Thay phần khớp: mọi chỗ khớp được thay bằng body; $1… là các nhóm của regex.
  • Chặn frame: frame bị bỏ.
  • Trễ frame: frame chờ số mili giây đã đặt; các frame phía sau vẫn giữ thứ tự.

Chỉ text frame bị đổi (binary frame đi qua nguyên vẹn); socket mở từ Web Worker hoặc iframe khác origin không được hỗ trợ; frame mà trang nhận sau khi rule đã đổi có event.isTrusted là false. Tải lại trang sau khi thêm rule WebSocket đầu tiên nếu socket đã mở từ trước.

9.14. Ngôn ngữ

Danh sách Ngôn ngữ cạnh Bật ghi đè chọn Tự động (theo ngôn ngữ trình duyệt), English hoặc Tiếng Việt. Chữ đổi ngay, lựa chọn được lưu trong trình duyệt này, và hướng dẫn sử dụng mở theo cùng ngôn ngữ.

9.15. Biến

Biến giữ ở một chỗ một giá trị bạn dùng trong nhiều rule, như host hay token. Bấm Biến trong tab Rules và thêm các cặp name: value, cho Site này (site đang mở trong panel) hoặc Mọi site. Giá trị của site thắng giá trị cùng tên dùng cho mọi site.

  • Viết {{name}} trong URL pattern, URL chuyển hướng, giá trị header của response hoặc request, response body (chế độ Text và response ngẫu nhiên) hoặc request body gửi lên server. Rule script đọc chúng qua request.vars.name.
  • Tên bắt đầu bằng chữ cái hoặc _, sau đó là chữ, số, _, . hoặc -. Tên của các placeholder có sẵn (now, timestamp, epoch, uuid) không dùng được.
  • {{name}} mà không biến nào định nghĩa thì giữ nguyên, và giá trị được thay vào một lần: {{name}} bên trong giá trị không được thay tiếp (trong body, placeholder có sẵn bên trong giá trị, như {{$uuid}}, vẫn được điền). \{{name}} giữ nguyên {{name}} như đã viết.
  • Biến không được thay trong rule WebSocket, điều kiện của request, giá trị patch hay JS/CSS được chèn.
  • Khi tắt điền placeholder {{...}}, body được gửi đúng như đã viết, kể cả biến; pattern và header vẫn được thay.
  • Lưu biến là áp dụng ngay. Biến được lưu trong trình duyệt cùng với rule, không nằm trong file rule xuất ra hay profile.

10. Lưu ý quan trọng

10.1. Phạm vi

  • Rule chỉ áp dụng cho tab đang được gắn.
  • Mỗi lần bật ON, extension gắn vào tab đang mở.
  • Chuyển sang tab khác thì tab mới chưa có ghi đè cho tới khi bạn bật lại.

10.2. Giới hạn dung lượng

  • Tối đa 500 URL trong danh sách API gần đây.
  • Tối đa 100 response body được lưu.
  • Khi vượt quá, mục cũ nhất bị bỏ trước (FIFO).

10.3. Lưu body

  • Chỉ response body của XHR và Fetch được lưu (để tự điền).
  • Các loại khác (JS, CSS, ảnh...) không được lưu.

10.4. Phụ thuộc Tab ID

API gần đây và response body được lưu theo tabId. Khi đóng tab rồi mở lại, tabId mới khác → dữ liệu cũ không hiện.

10.5. Không dùng cho production

Extension này chỉ dành cho developer debug. Đừng dùng trong môi trường production của người dùng cuối.

10.6. Quyền cần có

  • debugger — để chặn network request.
  • storage — để lưu rule và dữ liệu.
  • <all_urls> — để gắn debugger vào bất kỳ tab nào.

10.7. Thông báo lưu và áp dụng

Các thao tác với rule báo kết quả bằng thông báo ở góc trên bên phải:

  • Xanh lá: thay đổi đã được lưu và áp dụng cho tab hiện tại.
  • Vàng: thay đổi đã được lưu, nhưng không cập nhật được việc chặn. Thường là do một debugger hoặc phiên DevTools khác đang giữ tab. Bấm Thử lại trong thông báo sau khi xử lý xung đột; không cần lưu lại rule.
  • Đỏ: thao tác thất bại và chưa được lưu. Thông báo có kèm lỗi storage, import, profile hoặc background nếu có.

Lỗi kiểm tra dữ liệu trong modal hiện ngay phía trên Lưu rule. Modal vẫn mở và focus vào field cần sửa. Trong lúc lưu, nút hiện Đang lưu… và không bấm lần hai được.

11. FAQ

H: Rule không chạy?
Kiểm tra:
  1. Bật ghi đè đã bật chưa?
  2. Pattern có khớp URL không? Thử * để khớp tất cả.
  3. Tab hiện tại có phải tab đang được debug không? Thử tải lại extension.
  4. Mở DevTools → Console của extension để xem lỗi.
H: Đã bấm Lưu rule mà không thấy gì xảy ra?
Xem thông báo phía trên nút Lưu và thông báo ở góc trên bên phải. Màu đỏ nghĩa là rule chưa được lưu. Màu vàng nghĩa là rule đã lưu nhưng chưa áp dụng được cho tab hiện tại; đóng phiên DevTools/debugger đang tranh tab rồi bấm Thử lại trong thông báo đó.
H: Đã tắt ghi đè mà request vẫn bị đổi?
Thử tải lại trang. Nếu vẫn bị, tắt rồi bật lại extension.
H: Làm sao xóa hết rule một lần?
Vào tab Rule và bấm Xóa trên từng rule. Chưa có nút "Xóa tất cả".
H: Extension không chạy ở chế độ ẩn danh?
Vào chrome://extensions → bấm Details của extension → bật Allow in incognito.
H: Làm sao biết một request đã bị ghi đè?
Xem tab Network của DevTools:
  • Có thêm response header x-network-overrides: true.
  • Trong extension, API đó được tô xanh và nằm trong tab Đã ghi đè.
H: API không hiện trong tab API đã bắt?
Bấm Làm mới danh sách request. Extension tự thử lại trong một lúc ngắn. Nếu danh sách vẫn rỗng:
  1. Kiểm tra công tắc đang ON.
  2. Xem tab Network để chắc request có được gửi đi.
  3. Thử dùng DevTools panel thay vì popup.
H: Có ghi đè được WebSocket không?
Được, với các text frame mà trang gửi hoặc nhận qua WebSocket: thay, thay một phần, chặn hoặc làm trễ chúng bằng rule WebSocket. Xem 9.13.
H: Có dùng sync storage không?
Không. Extension dùng chrome.storage.local (giới hạn 10MB). Không dùng sync storage vì rule có thể chứa response body lớn.
H: Nhập được rule xuất từ domain khác không?
Được. Nhập luôn ghi vào domain đang mở trong panel, bất kể field domain của file ghi domain nào — nhưng nếu field đó không khớp domain hiện tại, hộp thoại nhập sẽ cảnh báo trước, nên không có chuyện lệch mà không biết. Nếu đã có rule, hộp thoại tiếp theo cho chọn rõ Thêm vào cuối hoặc Thay toàn bộ.
