1. Introduction

Network Overrides DevTools is a Chrome/Edge extension for developers that intercepts and overrides API response data directly in the browser, without modifying backend code.

Common use cases

  • Mock API responses to test the frontend when the backend isn't ready.
  • Debug by altering responses to simulate different states (errors, empty data, edge cases).
  • Redirect requests from an old API to a new one without changing frontend code.
  • Quickly inspect captured API requests and copy them as cURL commands.

2. Installation

Requirements

  • Chrome or Microsoft Edge (latest version).
  • Extension loaded as unpacked from source.

Steps

  1. Open chrome://extensions (or edge://extensions).
  2. Enable Developer mode (top right).
  3. Click Load unpacked.
  4. Select the project root directory (the folder containing manifest.json).
  5. The extension icon will appear on the toolbar.

Verify

  • The extension icon appears on the toolbar.
  • Open DevTools (F12) → Overrides tab.

3. Interface Overview

3.1. Popup

Click the extension icon on the toolbar. Contains:

  • Header: "Network Overrides API" with two compact actions: Refresh captured requests and Open user guide.
  • Enable Overrides toggle: Turn override functionality on/off.
  • Language: Auto, English or Tiếng Việt (see 9.14).
  • 3 tabs:
    • Captured APIs (N): List of captured requests with real-time counters, grouped by resource type (XHR, Fetch, Doc, JS, CSS).
    • Overridden (N): Real-time counter of APIs currently matched by an active rule.
    • Rules (N): Total count and list of all saved override rules.
  • Search bar: Filter APIs by URL substring.

3.2. DevTools Panel

Open DevTools (F12) → Overrides tab. Same as popup, plus:

  • Manual editor: A quick-add form (pattern + body) above the Rules tab.
  • HAR auto-load: Automatically loads request history from chrome.devtools.network.getHAR() on panel open.

3.3. Override Modal

Click Mock this on an API (or the API row) to open the modal. It shows the everyday fields first:

  • Presets: one click fills the fields below. Empty list (status 200 and [], or the JSON object with its lists emptied), Server error (status 500), Slow (3 s) (a 3000 ms delay), Offline (a network error, InternetDisconnected), and No CSP and No cache, which keep the real response and remove its Content-Security-Policy or caching headers (see 6.10).
  • URL pattern: URL pattern for matching. It starts as the URL of the request and can be edited: use * to match more URLs, e.g. /api/users/*.
  • Method: Dropdown (Any, GET, POST, PUT, PATCH, DELETE) to scope the rule to a specific request method. Defaults to Any, which matches every method. Pre-filled from the captured request's method when opening the modal from a captured API.
  • Mock response / Redirect / Network error / WebSocket: Choose the rule type.
  • Status code (mock response): blank keeps the real status. Pre-filled from the captured request when it can carry a body.
  • Response body: Custom response content (for a mock response).
  • Redirect URL: Target URL with wildcard substitution support.
  • Format JSON: Pretty-print JSON body.
  • Save Override: Save the rule.

Everything else is in the collapsed Advanced section, in groups:

  • Conditions: GraphQL operation (see 5.8), query parameters, request headers and a text the request body must contain (see 5.7), and Apply on every site (global rule).
  • Timing & failure: Delay (ms); Simulate a network error for the Network error type (Failed, TimedOut, ConnectionRefused, NameNotResolved, InternetDisconnected; combine TimedOut with a long delay to simulate a real timeout); and Answer without calling the server (mock response: the request is answered in the browser before it is sent, so the server is never called and unreachable hosts still get the mock; blank status = 200; CORS preflights are answered for you).
  • Response headers: headers to add (one Header-Name: value per line; same names overwrite the original), and Headers to remove from the response (see 6.10).
  • Body type: patch & script: the response body is Text, Raw base64, Script (JavaScript), Patch the real JSON response (see 6.6) or Keep the real response (headers only) (see 6.10), and whether {{...}} placeholders are filled in.
  • Random responses: more answers for the rule, each with a weight, and a seed for a repeatable order (see 6.11).
  • Change the request: replace the request body sent to the server, and add or replace request headers.

A group that holds a value shows a count on its header and opens by itself when you edit the rule, so no setting is hidden.

4. Basic Usage

Step 1: Open the extension

  • Option A: Click the extension icon on the toolbar → popup opens.
  • Option B: Open DevTools (F12) → Overrides tab.

Step 2: Enable Overrides

Flip the Enable Overrides toggle ON.

The extension will attach the debugger to the current tab and start monitoring network requests.

Step 3: Capture APIs

Browse your application normally. API requests will appear automatically in the Captured APIs tab.

Step 4: Create an Override

Method 1 (Click API):

  1. Go to Captured APIs or Overridden tab.
  2. Click Mock this on the API you want to override (clicking the row does the same). If a rule already covers the API, that rule opens for editing instead.
  3. The modal opens with the pattern and the real status pre-filled, and the Method dropdown pre-selected to the captured request's method if it's one of GET/POST/PUT/PATCH/DELETE (otherwise it defaults to Any).
  4. If the API has a stored response body, it will be auto-filled.
  5. Edit the content → Save Override.

Method 2 (Manual — DevTools panel only):

  1. Go to the Rules tab.
  2. In the form above, enter a Pattern and Response body.
  3. Click Add override.

Step 5: Verify

  • Overridden APIs show a blue border in the list.
  • The Overridden tab shows the count and list of matched APIs.
  • The real response is replaced with your custom content.

Step 6: Disable

  • Toggle the switch OFF to disable all overrides.
  • Or go to Rules tab → click Delete on a specific rule.

5. URL Patterns

5.1. Substring (default)

Any URL containing the pattern string is a match.

Pattern:  /api/users
Matches:  https://example.com/api/users
          https://example.com/api/users/123
          https://example.com/v2/api/users/list
No match: https://example.com/api/admin

5.2. Wildcard *

Use * to match any URL segment. Each * also captures the matched value for use in Redirect URLs. 

Pattern:  /api/*/users/*
Matches:  /api/v1/users/123  → captures: ["v1", "123"]
          /api/v2/users/abc  → captures: ["v2", "abc"]

5.3. Regex /pattern/flags

Patterns starting and ending with / are treated as regex. Optional flags follow the closing /. 

Pattern:  /\/api\/v\d+\/users/i
Matches:  /api/v1/users (case-insensitive)
          /API/V2/Users
No match: /api/admin/users
Pattern:  /\/api\/user\/(\d+)/
Matches:  /api/user/42 (captures: ["42"])

5.4. Match everything

Pattern: *
Pattern: all

Matches every request.

5.5. Rule order

Rules are evaluated in list order. The first matching rule wins. To change priority, drag a rule by its ⠿ handle and drop it on the upper or lower half of another rule, or focus the handle and press the up or down arrow key. The new order is saved at once. Domain rules always run before global rules, so a rule moves only within its own group.

5.6. HTTP method

Besides the URL pattern, a rule can also be scoped to a specific HTTP method via the Method field in the override modal (see 3.3 and 4). A rule with a specific method (GET, POST, PUT, PATCH, DELETE) only applies to requests using that method; Any (the default) matches every method, regardless of pattern type.

5.7. Query, header and body conditions

Open Advanced → Conditions in the modal to narrow a rule to some requests of the same URL. Every condition you fill in must hold, together with the pattern and method. Leave them empty and the rule matches as before.

  • Query parameters: write them as in a URL, for example page=2&debug. page=2 needs page to equal 2 (one of its values, if it repeats; compared after URL decoding). debug alone needs debug to be present, with any value. Names are case-sensitive.
  • Request headers: one per line. X-Tenant: acme needs that header with that exact value; Authorization alone needs the header to be present. Header names ignore case.
  • Request body contains: the request body must contain this text, for example "plan":"pro". Case matters. If the browser does not hand the body to the extension (for example a streamed upload), the condition does not match.

A rule's line in the rules list shows its conditions, such as + query page=2. A CORS preflight carries neither the headers nor the body of the request behind it, so only the query conditions are checked for the preflight.

5.8. GraphQL operation

The GraphQL operation field narrows a rule to one operation sent to a shared URL such as /graphql. It matches when the JSON request body's operationName equals the value (case-insensitive), failing that when its query contains the value, failing that when the raw body contains it. Requests without a body do not match.

6. Override Body

6.1. Text mode

Content is base64-encoded and returned as the response body.

{
  "status": "ok",
  "data": [
    { "id": 1, "name": "Alice" },
    { "id": 2, "name": "Bob" }
  ]
}

6.2. Raw base64 mode

Use when you already have base64-encoded content (e.g., binary data, images, pre-encoded files).

6.3. Body type badge

  • text — Content is not valid JSON.
  • json — Content is valid JSON (auto-detected as you type).

6.4. Format JSON

Click Format JSON to pretty-print the response body. If the content is not valid JSON, the editor says so and changes nothing.

6.5. Auto-fill

When creating a new override from an API:

  • If the API has a stored response body (in recentApiBodies), it is pre-filled automatically.
  • Otherwise, the extension sends a getApiData message to the background worker to retrieve the stored body.
  • This feature only works when Auto-fill on open is enabled (default: on).

6.6. Patch the real JSON response

Pick Patch the real JSON response in the Response body mode list when you want the real data with a few fields changed, for example to turn on a paid plan or hide a banner. The request goes to the server; the rule changes only the fields you list in its JSON response. Write one change per line: 

set data.user.plan = "pro"
remove data.ads
set data.items[0].price = 0
set data.flags = {"beta": true}
  • set <path> = <value> puts a value at the path. The value is JSON: write text in double quotes ("pro"), and numbers, true, false, null, objects and arrays as they are.
  • remove <path> deletes a field, or an array item (the items after it move up).
  • A path uses dots for fields and [0] for array items: data.items[0].name. A key with dots, spaces or = goes in quotes: data["user.name"]. A path that starts with / is a JSON Pointer: /data/items/0/name.
  • [-] (or - in a JSON Pointer) means the end of an array: set data.items[-] = {"id": 99} appends an item.
  • When a set path does not exist yet, the missing objects are created (an array when the next part is [0] or [-]). A remove of something that is not there does nothing.

The real status and headers are kept; Status code, Response headers and Delay still apply when you fill them. Content-Length is worked out again for the new body. The JSON is sent back compact. Templates are not processed in patch values, and Answer without calling the server is not offered, since a patch needs the real response.

When the response is not JSON or has no body (an HTML page, a 204, a redirect), it passes through unchanged and the panel shows a warning. A change that cannot apply, such as a path through a text field or an array index past the end, is skipped and named in the same warning; the other changes still apply. The rule's line in the Rules tab ends with patch N fields; hover it to see the changes.

6.7. Script responses

With the body mode Script (JavaScript) the rule computes its response. The body is the body of an async function that receives request and returns the response: 

// Keep the real response, but only its first three items.
const data = JSON.parse(request.response.body);
return { status: 200, body: { ...data, items: data.items.slice(0, 3) } };
  • request holds url, method, headers (lower-case names), query, params (what each * matched), body, response (the original status, headers and body) and vars (your variables, see 9.15).
  • Return a string for the body, { status, headers, body }, or any other value to send it as JSON. A returned status or header wins over the rule's own; the delay still applies. Templates are not processed in a script.
  • The script runs in the inspected page, so it can use fetch, localStorage and the page's globals. It has 5 seconds; a script that throws, returns nothing or times out answers with status 500 and the header x-network-overrides-error: script.
  • Imported rules may contain scripts, which run in the pages they match: import only files you trust.

6.8. Replace a static file

A Mock response rule also answers scripts, stylesheets, images, fonts and pages. Point the URL pattern at the file, for example /static/app.js, and click Use a local file… under the response body:

  • A text file (JS, CSS, HTML, JSON, SVG, XML) goes into the body box, where you can still edit it. Any other file (an image, a font) is kept as it is and shown as From file name (size), with a Remove file button.
  • The Content-Type is set from the file and can be changed under Advanced → Response headers. The rule answers with status 200 unless you set another, so a file the server does not have (404) still loads.
  • Rules are kept in browser storage, which holds about 10 MB in all. Above 2 MB the editor warns you; keep large files small, or replace only the file you are working on.
  • While a tab is intercepted its browser cache is bypassed, so a rule also applies to a file the page had cached. Reload the page after adding the rule.
  • A page script or stylesheet with an integrity attribute (SRI) refuses a replaced file. Requests a service worker answers itself are not intercepted.

6.9. Inject JS/CSS into a page

Choose the type Inject JS/CSS to add your own code to the pages a rule matches, such as https://example.com/*. The real page still loads; the rule only adds to it.

  • The stylesheet goes at the end of <head>; the script goes at the end of <body>, so the page's elements already exist when it runs.
  • Only pages (documents) are changed, not API calls, and only successful (2xx) UTF-8 HTML responses. Other rules, such as API mocks, keep working on the same page.
  • A page with a Content-Security-Policy keeps it. The SHA-256 hash of the injected script and stylesheet is added to the policy, so exactly that code runs while the page's own inline code and every other rule of the policy stay as they were. A CSP sandbox without allow-scripts still stops the script; the panel then warns you.
  • If your code loads other scripts, uses eval or inline event handlers, the policy may still block that part. Tick Remove the page's Content-Security-Policy in the rule as a last resort: the matched pages then load without their CSP while the rule is on, which lowers their protection.
  • Reload the page after adding or changing the rule.

6.10. Keep the real response, remove headers

A rule can drop headers from a response, for example a Content-Security-Policy that stops your debugging, or the caching headers that keep an old file around.

  • Pick Keep the real response (headers only) under Advanced → Body type to leave the server's body as it is. The request goes to the server; only the status (when you set one) and the headers change. The No CSP and No cache presets set this up in one click.
  • List the headers under Advanced → Response headers → Headers to remove from the response, one per line or separated by commas. Case does not matter. A name ending in * removes every header that starts with it: x-debug-*.
  • Removal works with every mock response too: the server's headers are removed first, then the rule's own response headers are added. So you can remove Cache-Control and add Cache-Control: no-store.
  • The extension's marker headers are never removed.
  • A response whose body cannot be read, such as a redirect, passes through unchanged and the panel warns you. Answer without calling the server is not offered, since the rule needs the real response.

6.11. Random responses by weight

A Mock response rule (Text or Raw base64 body) can answer with one of several responses, to see how a page copes with a flaky API. Write the usual body and status: this is the first response. Then open Advanced → Random responses, click + Add a response and fill its weight, status (blank keeps the rule's), body and headers (Name: value, added over the rule's headers). Weight of the response above is the weight of the first response (blank is 1).

  • Each request gets one response, picked by weight: weights 80 and 20 give the first one about 8 times in 10. A weight of 0 is never picked. Templates and variables work in every body.
  • The answer carries the header x-network-overrides-response: the number of the response it gave (1 is the rule's own).
  • Seed (repeatable order): blank picks at random. With a number the picks follow the same order every time, which suits automated tests. The order follows how many times the rule was applied, so it goes on across a worker restart; Reset counts, or an edit of the rule, starts it over.

7. Redirect URL

7.1. How it works

When you choose the Redirect type, instead of overriding the response body, the extension redirects the request at the request stage (before the actual request is sent).

7.2. Wildcard substitution

Use * in the Redirect URL to substitute captured values from the pattern match.

Pattern Request URL Captures Redirect URL Result
/api/* https://site.com/api/user ["user"] https://site.com/api/v2/* https://site.com/api/v2/user
/api/old/*/data /api/old/v1/data ["v1"] /api/new/*/data /api/new/v1/data
https://old.com/*/item/* https://old.com/shop/item/5 ["shop","5"] https://new.com/*/product/* https://new.com/shop/product/5

If any * remains unsubstituted, the extension logs an error and lets the request proceed normally (no redirect).

Common mistake: Pattern has 1 * but Redirect URL has 2:

Pattern Request URL Captures Redirect URL Result
https://site.com/api/* https://site.com/api/user ["user"] https://site.com/api/v2/** ❌ second * not substituted

7.3. When to use

  • Redirect from an old API to a new API without changing frontend code.
  • Point requests from production to a staging/local server for debugging.
  • Suppress certain requests by redirecting to an empty endpoint.

8. Managing Rules

8.1. View rules

Go to the Rules tab. Each rule displays:

  • Enabled checkbox: at the start of the row. Unchecked means the rule is disabled (see 8.5).
  • GLOBAL badge: the rule applies on every site.
  • One-line summary: what the rule matches → what it does, for example GET /api/orders + query page=2 → 500 · slow 3 s, POST /graphql (op: GetUser) → patch 2 fields, /api/* → network error or ws wss://example.com/socket → replace frames. Hover it for the details; click it to open the editor.
  • Applied count: a small number after the rule, the times it was applied in this session. 0 is grey, a higher number is blue. Hover it (or move to it with Tab) to see when the rule was last applied and to which URL. A request counts when the rule really changes it. An enabled rule still at 0 after requests went by gets a dashed outline: check its pattern, method and conditions. The count follows the rule when you reorder it or turn it off and on, and starts again when you edit it. Reset counts above the list sets every count back to 0, and so does turning interception off. Counts are never saved, exported or imported with the rules.

8.2. Edit a rule

Click Edit next to a rule (or its summary) → modal opens with current values → edit → Save Override. Copy duplicates a rule.

8.3. Delete a rule

Click Delete → rule is removed immediately.

8.4. Persistence

Rules are stored in chrome.storage.local → they never disappear on page refresh, DevTools close, or browser restart.

8.5. Enable/disable a rule

Each rule has a checkbox at the start of its row. Unchecking it disables the rule (enabled: false) without deleting it:

  • The rule stays visible in the Rules list, dimmed.
  • Any API it targets stays in the Overridden tab (it still "would apply" by pattern and method) but is also shown dimmed, since a disabled rule is no longer actively applied.
  • The background service worker skips disabled rules when deciding which override to apply to a request.

Checking the box re-enables the rule. New rules, and rules that existed before this feature was added, default to enabled.

8.6. Export rules

Click Export in the Rules tab to download the rules for the currently active domain as a JSON file (named after the domain). The file has this shape: 

{
  "version": 1,
  "domain": "https://example.com",
  "exportedAt": "2026-07-07T00:00:00.000Z",
  "overrides": [
    /* OverrideRule[] */
  ]
}

Export only includes rules for the domain currently open in the panel, not all domains.

8.7. Import rules

Click Import → Rules file (.json) in the Rules tab and pick a previously exported (or hand-crafted) JSON file:

  • If the file's domain field is present and doesn't match the domain currently active in the panel, a confirm dialog warns you and asks whether to import into the current domain anyway. Canceling aborts the import with no changes.
  • If the current domain already has rules, a dialog asks how to combine them: Append rules adds the imported rules to the end of the existing list; Replace rules overwrites all existing rules for the current domain with the imported ones. Closing the dialog cancels the import.
  • If the current domain has no rules yet, the import is applied directly with no prompt.
  • Invalid files (not valid JSON, missing the overrides array, or a rule missing required fields) are rejected with an alert, and nothing is changed.
  • Only known rule fields (pattern, mode, body, redirectUrl, method, enabled) are kept from each imported rule; any other properties in the file are dropped.
  • The match conditions matchQuery, matchHeaders and matchBody (see 5.7) are kept too. Files exported before they existed import unchanged.
  • A patch rule ("mode": "patch", see 6.6) keeps its patch list of { "op": "set" | "remove", "path": "...", "value": ... } operations. A file whose patch operations are malformed is rejected like any other invalid file.
  • removeResponseHeaders, "mode": "passthrough" and the random responses (responses, weight, randomSeed) are kept too. Variables are not part of the file.

Like Export, Import always operates on the domain currently active in the panel — never all domains at once.

9. Additional Features

9.1. Copy cURL

Each API entry has a cURL button. Click to copy the request as a cURL command: 

curl 'https://api.example.com/data' \
  -X 'POST' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer xxx' \
  --data-raw '{"key":"value"}'

9.2. Search APIs

Search box in the Captured APIs and Overridden tabs. Searches by URL substring (case-insensitive). Matching text is highlighted with a yellow background.

9.3. Refresh API list

Click Refresh captured requests in the header or the refresh action beside the captured-request filters. The icon spins and is temporarily disabled while the current API snapshot is loaded. If the list is empty, the extension retries automatically.

9.4. Open the user guide

Click Open user guide in the header. The complete guide opens in a separate browser tab, so the popup or DevTools panel remains available. It opens in the language the extension shows: the Vietnamese guide when the UI is in Tiếng Việt, this English guide otherwise.

9.5. Type grouping

APIs are grouped by resource type: XHR, Fetch, JS, CSS, Img, Media, Font, Doc, WS, Manifest, EventSource, TextTrack, Other.

Click a group header to collapse/expand. Collapse state is persisted in storage.

9.6. Marker headers

When a request is overridden, the extension adds these response headers:

  • x-network-overrides: true
  • x-network-overrides-pattern: <pattern>
  • x-network-overrides-response: <n>, only for a rule with random responses: which response it gave

This lets you easily identify overridden requests in the DevTools Network tab.

9.7. Dynamic Response Templating

Insert dynamic placeholders into mock response bodies:

  • {{$uuid}} — Random UUID v4
  • {{$isoDate}} — ISO 8601 timestamp
  • {{$epoch}} — Unix timestamp in ms
  • {{$randomEmail}} — Random email address
  • {{$randomName}} — Random full name
  • {{$randomInt(1, 100)}} — Random integer in range
  • {{$query(name)}} — Query parameter value from request URL
  • {{$jwt}} — A well-formed fake JWT with sub, iat (now) and exp (now + 1 hour). Add claims with a JSON object and set the lifetime in seconds: {{$jwt({"sub":"42","role":"admin"}, 300)}}. A negative lifetime gives an expired token; inside a JSON string the quotes may be written as \". It is not validly signed: the signature is random, so it suits code that only decodes the token, not a check of the signature.

9.8. Global Cross-Domain Rules

Tick Advanced → Conditions → Apply on every site (global rule) to intercept matching requests across all domains. Global rules display a GLOBAL badge in the rules list.

9.9. Request Payload Modification

Override outgoing POST, PUT, or PATCH request payloads before they reach the server, under Advanced → Change the request.

9.10. Network Throttling and Traffic Analytics

Use the Network selector to simulate Fast 3G, Slow 3G, or Offline conditions for the attached tab. Live counters show overridden and failed requests and survive service-worker restarts.

9.11. HAR File Import

In the Rules tab, click Import → cURL or OpenAPI / Swagger… and paste or choose a .har file (HTTP Archive) to generate mock rules in bulk from recorded traffic. The same dialog takes a cURL command or an OpenAPI / Swagger spec.

9.12. Editor Keyboard Shortcuts

  • Ctrl + Enter / Cmd + Enter — Save override rule
  • Ctrl + Shift + F / Cmd + Shift + F — Format JSON body

9.13. WebSocket frames

To change what a WebSocket carries, open the override dialog (or click a WS entry in the API list) and choose WebSocket frames. A rule matches the socket URL (wss://api.example.com/*), the direction (send, receive or both) and optionally the frame text (contains, or a regular expression). The first enabled rule that fits is applied:

  • Replace: the frame becomes the body (templates such as {{now}} work).
  • Substitute: every match is replaced by the body; $1… refer to regex groups.
  • Block: the frame is dropped.
  • Delay: the frame waits the given milliseconds; frames behind it keep their order.

Only text frames are changed (binary frames pass untouched); sockets opened from Web Workers or cross-origin iframes are not covered; frames the page receives after a rule changed them have event.isTrusted set to false. Reload the page after adding the first WebSocket rule if the socket was already open.

9.14. Language

The Language list next to Enable Overrides picks Auto (the browser's language), English or Tiếng Việt. The text changes at once, the choice is saved in this browser, and the user guide opens in the same language.

9.15. Variables

Variables keep a value you use in many rules, such as a host or a token, in one place. Click Variables in the Rules tab and add name: value pairs, for This site (the site open in the panel) or Every site. A site value wins over one of the same name for every site.

  • Write {{name}} in a URL pattern, a redirect URL, a response or request header value, a response body (Text mode and random responses) or the request body sent to the server. Script rules read them as request.vars.name.
  • A name starts with a letter or _, then letters, digits, _, . or -. The names of the built-in placeholders (now, timestamp, epoch, uuid) are taken.
  • A {{name}} no variable defines is left as written, and a value is put in once: a {{name}} inside a value is not filled again (in a body, a built-in placeholder inside a value, such as {{$uuid}}, still is). \{{name}} keeps {{name}} as written.
  • Variables are not filled in WebSocket rules, request conditions, patch values or injected JS/CSS.
  • With Fill in {{...}} placeholders off, a body is sent exactly as written, variables included; patterns and headers are still filled.
  • Saving applies the variables at once. They are stored in the browser with the rules, not in exported rule files or profiles.

10. Important Notes

10.1. Scope

  • Overrides only apply to the currently attached tab.
  • Each time you toggle ON, the extension attaches to the active tab.
  • Switching to another tab disables overrides for the new tab until you toggle again.

10.2. Capacity limits

  • Maximum 500 URLs in the recent APIs list.
  • Maximum 100 response bodies stored.
  • When exceeded, the oldest entries are evicted (FIFO).

10.3. Body storage

  • Only XHR and Fetch resource types have their response bodies stored (for auto-fill).
  • Other types (JS, CSS, Image, etc.) are not stored.

10.4. Tab ID dependency

Recent APIs and response bodies are keyed by tabId. When you close a tab and reopen it, the new tabId differs → old data is not shown.

10.5. Not for production use

This extension is designed for developer debugging only. Do not use it in end-user production environments.

10.6. Required permissions

  • debugger — to intercept network requests.
  • storage — to persist rules and data.
  • <all_urls> — to attach the debugger to any tab.

10.7. Save and apply notifications

Rule operations now report their result in a notification at the top-right:

  • Green: the change was saved and applied to the active tab.
  • Yellow: the change was saved, but interception could not be updated. This commonly means another debugger or DevTools session owns the tab. Use Retry in the notification after resolving the conflict; the rule does not need to be saved again.
  • Red: the operation failed and was not saved. The message includes the storage, import, profile, or background error when available.

Validation errors inside the Override editor appear directly above Save Override. The editor stays open and focuses the field that needs to be corrected. While persistence is running, the button displays Saving… and cannot be pressed twice.

11. FAQ

Q: Override not working?
Checklist:
  1. Is Enable Overrides turned ON?
  2. Does the pattern match the URL? Try * to match everything.
  3. Is the current tab the one being debugged? Try refreshing the extension.
  4. Open DevTools → extension's Console to check for errors.
Q: I clicked Save Override, but nothing appeared to happen?
Check the message above the Save button and the notification in the top-right corner. A red message means the rule was not stored. A yellow notification means the rule was stored but could not be applied to the active tab; close any competing DevTools/debugger session and click Retry in that notification.
Q: Turned off overrides but requests are still being modified?
Try refreshing the page. If the issue persists, disable and re-enable the extension.
Q: How do I delete all rules at once?
Go to the Rules tab and click Delete on each rule. There is no "Clear all" button.
Q: Extension doesn't work in incognito mode?
Go to chrome://extensions → click Details on the extension → enable Allow in incognito.
Q: How can I tell if a request was overridden?
Check the DevTools Network tab:
  • Response header x-network-overrides: true is added.
  • In the extension, the API entry is highlighted in blue and appears in the Overridden tab.
Q: APIs are not showing up in Captured APIs?
Click Refresh captured requests. The extension retries automatically for a short period. If the list is still empty:
  1. Verify the toggle is ON.
  2. Check the Network tab to confirm requests are being sent.
  3. Try the DevTools panel instead of the popup.
Q: Can I override WebSocket connections?
Yes, the text frames a page sends or receives on a WebSocket: replace, substitute, block or delay them with a WebSocket frames rule. See 9.13.
Q: Does this support sync storage?
No. The extension uses chrome.storage.local (10MB limit). Sync storage is not used since rules may contain large response bodies.
Q: Can I import rules exported from a different domain?
Yes. Import always writes into the domain that's currently active in the panel, regardless of which domain the file's domain field says it was exported from — but if that field doesn't match the current domain, an import dialog warns you first, so the mismatch isn't silent. If rules already exist, the next dialog provides explicit Append rules and Replace rules choices.
